# تصحيح تنبيهات «سلامة البيانات» على صفحة الشركة

## نتيجة التحقق
الملاحظة `80df4e61-da79-5b5a-9888-63cdf427f69a` مؤكدة في النسخة الحالية: البطاقة تطلب الدفعات والمستحقات، لكنها تحسب الأرصدة باستخدام التحويلات دون طلب تحميلها. تحميل الشركة قد يُتخطّى عندما تكون التفاصيل محمّلة، فلا يضمن فتح الشركة مباشرة اكتمال التحويلات.

الملف جاء عبر GitHub PR #150، وبطاقة «سلامة البيانات» محمية صراحة في `docs/LOVABLE_HANDOFF.md`. التنفيذ لفريق Claude / المطوّر عبر GitHub، وليس إذناً لـ Lovable بتعديل الملفات المحمية. لم يُطبَّق إصلاح ولم تُوسم الملاحظة بأنها محلولة.

## الإصلاح المحدود
1. تحميل التحويلات النقدية لكل مشروع تعرضه البطاقة، مع الدفعات والمستحقات الحالية، باستخدام إجراء التحميل الموجود.
2. عدم عرض حكم «الحسابات مغلقة» أو تنبيهات الأرصدة قبل اكتمال تحميل المدخلات؛ عند فشل التحميل تُعرض حالة تعذّر الفحص بدلاً من اعتبار قائمة التحويلات الفارغة بيانات صحيحة.
3. إبقاء معادلات الأرصدة وصلاحيات الوصول والبيانات المحفوظة كما هي. لا حاجة إلى ترحيل قاعدة بيانات.

## تفاصيل تقنية لفريق GitHub
- التعديل الرئيسي: `src/pages/company/IntegrityCard.tsx`؛ إضافة `loadCashTransfersForProject` للتحميل والاعتماديات، وتجميع الطلبات مع حالة اكتمال/فشل محلية وإهمال نتائج الطلبات القديمة عند تغيير مجموعة المشاريع.
- استخدام إجراء المخزن القائم فقط؛ لا وصول مباشر إلى قاعدة البيانات من البطاقة.
- مصدر الحساب الحالي صحيح: `getCustodyRemaining` يضيف التحويلات الواردة، و`getFundRemaining` يخصم التحويلات الصادرة؛ المشكلة اكتمال المدخلات وليست المعادلات.
- مراجعة المسارات الشقيقة التي تستدعي `checkIntegrity` للتأكد من تحميل التحويلات قبل الحكم، دون توسيع نطاق التعديلات غير اللازمة.

## التحقق قبل الدمج
- فتح الشركة مباشرة بمخزن يحتوي `detailsLoaded: true` وتحويلات غير محمّلة: التأكد من طلب تحويلات جميع مشاريع الشركة دون زيارة المشروع أولاً.
- حالة عهدة أصلها 5,000 وتحويل وارد 3,000 ومصروف 7,000: المتبقي 1,000، ولا يظهر `custody_over` بعد اكتمال التحميل.
- حالة مشروع منتهٍ: دفعة 8,000 وعهدة أصلها 5,000 وتحويل إضافي صادر 3,000؛ صرف العهدة 8,000، فيصبح رصيد الدفعة والعهدة صفراً، ولا يظهر `cash_left_finished` بسبب التحويل الناقص.
- تأخير التحويلات ثم رفض طلبها: لا حكم على الأرصدة أثناء الانتظار، ولا رسالة نجاح عند الفشل.
- إثبات تمييز الاختبار: تعطيل تحميل التحويلات مؤقتاً يجعل اختبار الدخول المباشر يفشل، ثم إعادته قبل الدمج.
- تشغيل الاختبارات ذات الصلة بالبطاقة والشركة والمخزن، ثم بوابات Quality المعتادة في GitHub. فحص الواجهة بحساب مخوّل على شركة لها تحويلات فعلية، مع إعادة تحميل الصفحة مباشرة.

## معيار الإغلاق
تُغلق الملاحظة بوصفها `fixed` فقط بعد دمج الإصلاح والتحقق من الأرصدة في مسار الدخول المباشر للشركة؛ تبقى مفتوحة حتى ذلك الحين.
