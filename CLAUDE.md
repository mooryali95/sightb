# Working rules for this repository

Conventions that were learned the expensive way here. Each one exists because
something broke, not because it sounded tidy.

## 1. Never hand the owner SQL to run by hand

**Verification belongs in CI, not in a script pasted into a database console.**

Three separate times this project was verified by sending the owner a `.sql`
file to run in the Supabase editor and paste results back. That is the wrong
shape for three reasons:

- it costs the owner a round-trip every time, and the answer is stale the
  moment anything merges;
- one of those scripts had eight statements, and the Supabase editor returns
  only the last result set — seven checks were silently swallowed and the
  owner's time was spent for one answer;
- **it can draw down the Lovable workspace quota**, which meters usage and then
  stops and asks for payment.

The correct home for any database check is `scripts/security-scan.sh`, which
runs from the Security Re-scan workflow. That path runs on GitHub Actions and
talks to Supabase **directly** — it never touches Lovable, so it consumes none
of that quota.

If a check cannot run there, the reason is almost always the missing
`SUPABASE_DB_URL` secret, and the fix is to say so once rather than to work
around it with another hand-run script.

**Exception:** a genuine one-off that will never need repeating, where the cost
of automating exceeds the cost of asking. If a check would ever be run twice,
it goes in the scan.

## 2. Do not spend Lovable credits

`send_message` and `create_project` hand work to Lovable's own agent and
**consume the owner's workspace credits**. Do not call them to inspect,
verify, or fix anything that can be done from this repository.

Read-only Lovable calls (`list_projects`, `get_project`, `get_database_status`)
are fine for orientation.

Project reference: `sightb`, id `8e5cefc0-5a5c-4def-8a46-931108943957`,
workspace *Milestone Impact*, published at `sightb.lovable.app`.

## 3. Some files are regenerated by Lovable — do not fight them

Lovable pushes directly to `main`, and it rewrites files it owns. A fix
committed to one of those files gets reverted on the next push, byte for byte,
comments included.

`src/integrations/supabase/previewAuthStorage.ts` is one. Its `prefer-const`
violation was fixed in #12 and reverted by `cab503f`, turning `main` red for
three consecutive commits. It is now in the ESLint `ignores` list, and it stays
covered by the strict typecheck.

Before fixing a lint or style violation, check `git log` on that file. If
Lovable authored it, excluding it beats repairing it — a gate a generated file
can flip is a gate people learn to ignore.

## 4. Migrations merged through GitHub are not applied automatically

Proven against the live ledger, not assumed: two migrations sat in
`supabase/migrations` for days while the code depending on them was live.
Lovable applies the migrations *it* authors and ignores anything arriving
through git.

`.github/workflows/migrate.yml` closes this, but it needs the
`SUPABASE_PROD_DB_URL` secret. **Without that secret it skips silently** — it
does not fail, so a green run does not mean a migration was applied.

Edge functions have the same gap. Of the ten in `supabase/functions`, nine
answered on the live project on 23 September; `passkeys`, the one added
through git, answered 404. `.github/workflows/deploy-functions.yml` deploys a
function when its folder, or a shared file it imports, changes on main, and
can be run by hand for named functions. It needs the `SUPABASE_ACCESS_TOKEN`
secret; without it the run warns that nothing was deployed.

An applied migration must never leave the repository. Lovable deleted
`20260314014847_email_infra.sql` on 23 September while three functions still
used the table it creates; it was restored byte for byte. The live ledger
keeps a deleted version, so `supabase db push` refuses to run, and a database
rebuilt from the repository lacks the objects. The "Guard the migration
history" step in `quality.yml` fails on any deleted or renamed migration. If it
fires on a Lovable push, restore the file from the commit before; do not
delete the ledger row.

**On Lovable Cloud none of those secrets can exist.** The project is hosted
there, and the owner has no Supabase dashboard, cannot create an access token
and has no database URL. So `migrate.yml`, `deploy-functions.yml` and the
database checks in the security scan cannot be enabled while it stays there;
they are kept for a move off Lovable Cloud. What works instead:

- `scripts/live-drift.sh`, run by Security Re-scan on every push to main,
  every publish and nightly, needs no secret. It asks the live API with the
  publishable key in `.env` whether every table a migration creates and every
  function folder is live, and fails naming what is not. It would have caught
  the missing passkeys tables and function the day #92 merged.
- A migration merged through git is applied by the owner in Lovable Cloud's
  SQL editor, as a one-off under rule 1's exception. Hand them one idempotent
  block that records its version in `supabase_migrations.schema_migrations`
  and ends in a single verification row, since the editor shows only the last
  result. Test it on a local Postgres first, twice, and break the check once.
- A function arriving through git is deployed when Lovable next builds the
  project; `passkeys` went live that way.

`scripts/security-scan.sh` check 5/5 detects the drift. Version matching is on
real timestamps with a ±10s tolerance, never string or integer comparison:
`20260307175459` and `20260307175500` are one second apart but 41 apart
numerically.

## 5. The ESLint budget is a ratchet — it falls, never rises

`.github/workflows/quality.yml` holds `ERROR_BUDGET` and `WARN_BUDGET`. When
you clear violations, lower the budget in the same PR. When a push breaks it,
**fix the violation** — raising the budget to absorb new breakage defeats the
mechanism.

The first load is held the same way. `scripts/initial-load-guard.sh`, a
Quality step after the build, fails when the charts, PDF or spreadsheet chunk
loads before sign-in, and when the gzipped total passes its `GZIP_BUDGET_KB`.
Lower the budget when the first load shrinks; when it grows, load the new
weight where it is used instead of raising it.

Warnings are capped too, deliberately: `react-hooks/exhaustive-deps` reports at
warning severity, and a stale dependency array shows a stale balance in a
financial app.

## 6. `bun.lock` must resolve only from the public registry

It has twice arrived resolving packages from
`<region>-npm.pkg.dev/lovable-core-prod/sandbox-npm-cache`, a private Google
Artifact Registry — 176 packages once, four more (different region) on the next
Lovable push. Integrity hashes make this an **availability** risk, not a
tampering one, but a fresh clone breaks if that registry closes.

The "Guard the lockfile registry" step in `quality.yml` fails the build on any
`pkg.dev` host. Remedy is a plain host swap to `registry.npmjs.org` keeping
each `sha512` — then `bun install --frozen-lockfile` proves the content is
identical, because it refuses to amend the lockfile.

## 7. Prove it by running it

This repository has been burned repeatedly by checks that reported results they
never computed:

- `bun pm audit` is not a subcommand. Bun printed its help text, exited
  non-zero, and the script read that as "advisories found" — a dependency
  finding it had never computed.
- A job-level `if: ${{ secrets.X != '' }}` is invalid; the `secrets` context is
  unavailable there. Instead of skipping the job it failed the whole workflow
  before any job started: **66 runs, zero jobs, not one test executed.**
- SSOT Tests is green today only because every step is `skipped`. Green means
  "skipped", not "passed", until `SUPABASE_DB_URL` is set.

So: a tool that cannot run must fail loudly, never be counted as zero. Before
claiming a fix works, execute it — and where a claim is about behaviour,
deliberately break it once to confirm the check discriminates.

## 8. Gates to run before pushing

```bash
bun install --frozen-lockfile
bun run test                              # vitest
bun run typecheck:strict                  # tsc -p tsconfig.app.json
bun run build
bunx eslint .                             # must stay within the budget
bash scripts/security-scan.sh             # exits 0 without a DB URL
```

Plus the two greps in `quality.yml`: the data-access guard (production code
reaches the database only through `src/services`) and the lockfile registry
guard.
